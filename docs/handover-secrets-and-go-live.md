# Keys, access and going live

For Ladles of Love's IT person. How the system's keys are kept, who signs into what, and the
steps to move from our test setup to production.

## The rule

Nobody is handed a file of keys. Each person gets **their own login** to the places the keys
live, with two-factor authentication on, and sees only what their role needs. When someone
leaves, the owner removes their login; no key has to change.

| Where | What it holds | Who signs in |
|---|---|---|
| **Render** (the Batches service, Environment tab) | The live server's settings: every value in `server/env.example` | IT person and a backup, as Owners |
| **Bitwarden** (organisation vault, "Batches" collection) | A copy of every key, each with a note: which account it belongs to and what breaks if it changes | IT person and a backup |
| **Supabase** | The database, its backups and its connection string | IT person and a backup, as Owners |
| **Google Cloud** | The Gmail sending account's OAuth client, and the Gemini key | IT person |
| **Intuit developer** | The QuickBooks app keys | IT person |
| **Batches itself** | Business settings: cut-off hours, reminder time, expiry warnings, unit weights, recipe rounding and bands, collection days, translations | Admins, from Settings |
| **QuickBooks** | The finance company | Finance, connected from Batches > Settings > Connections |

Warehouse staff and managers only ever sign into Batches. They never see a key.

Two Owners on every account, so nobody is locked out if one person leaves.

## Day to day

- **Change a key or server setting:** Render > Batches service > Environment > edit > Save.
  Render redeploys with it. Then update the same entry in Bitwarden.
- **Check the server's setup:** Render > Shell, then `cd server && node scripts/check-env.mjs`.
  It lists what is set, missing or wrong, and never prints a value.
- **Change a business value** (rounding, bands, reminder time, wording): an admin does it in
  Batches > Settings. No developer needed.
- **Work on a laptop:** copy `server/env.example` to `server/.env`, fill it from Bitwarden, and
  point `DATABASE_URL` at a **separate test database**, never production. Run
  `npm run check-env`.

## Handover day

Easiest done together, in person or on a call, because every invite has to be accepted and
two-factor set up there and then.

1. Ladles creates a Bitwarden organisation and invites the student team for the day.
2. The team invites the IT person and a backup to Render, Supabase and Google Cloud as Owners,
   transfers the Supabase project, and (if wanted) recreates the Render service in Ladles' own
   workspace.
3. Ladles creates its own Gmail OAuth client, Intuit app, Gemini key and VAPID pair (see
   below), and enters them in Render and Bitwarden.
4. Run `check-env` on Render, then sign in, send a test email and generate a test picking slip.
5. Remove the student team from every account, and change any key the team ever had on a
   laptop.

## From testing to production

| Item | In testing | For production |
|---|---|---|
| `NODE_ENV` | unset | `production` (render.yaml sets it) |
| `APP_BASE_URL` | `http://localhost:5173` | the public `https://` address, no trailing slash |
| Gmail OAuth consent screen | "Testing": only listed test users, and the connection stops after 7 days | Google Cloud > OAuth consent screen > **Publish app**. Add the live redirect (`https://<address>/api/gmail/callback`) to the OAuth client and to `GMAIL_REDIRECT_URI` |
| `EMAIL_ENABLED` | may be `false` (emails only recorded) | unset or `true` |
| QuickBooks | `QUICKBOOKS_ENVIRONMENT=sandbox`, sandbox keys | `production`, the **production** keys from the Intuit app, and the live redirect (`https://<address>/api/quickbooks/callback`) |
| Database | a test database | Supabase production; set `DB_SSL_CA` so the certificate is checked |
| `TRUSTED_CLIENT_IP_HEADER` | unset | `cf-connecting-ip` on Render (render.yaml sets it) |
| `JWT_SECRET` | anything | generated by Render; never reused from a laptop |
| VAPID keys | optional | generate one pair (`npx web-push generate-vapid-keys`) and **keep it**: a new pair stops every phone's alerts |
| Render plan | free (sleeps after 15 minutes) | a paid instance, so the first scan of the morning does not wait a minute |

`npm run check-env` flags most of these on a live server (sandbox QuickBooks, a localhost
address, emails switched off, missing headers).
